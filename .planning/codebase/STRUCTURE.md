# Codebase Structure

**Analysis Date:** 2026-03-27

## Directory Layout

```text
[project-root]/
├── `meraki-mcp.py`              # Curated/manual MCP server with hand-written tools
├── `meraki-mcp-dynamic.py`      # Dynamic/hybrid MCP server with generic dispatcher and cache support

├── `entrypoint.sh`              # Container bootstrap that selects manual vs dynamic server

├── `pyproject.toml`             # Project metadata and core dependency declarations

├── `README-DYNAMIC.md`          # Dynamic server architecture and usage guide

├── `.planning/codebase/`        # Generated architecture/planning artifacts

└── `.claude/`                   # Local Claude-related workspace metadata
```

## Directory Purposes

**Project Root (`.`):**
- Purpose: Hold all executable source files, packaging files, docs, and deployment assets at the top level.
- Contains: `meraki-mcp.py`, `meraki-mcp-dynamic.py`, `inspect_tools.py`, container files, and all user-facing documentation
- Key files: `meraki-mcp.py`, `meraki-mcp-dynamic.py`, `entrypoint.sh`, `Dockerfile`, `docker-compose.yml`

**Dynamic Cache Directory (`.meraki_cache/`):**
- Purpose: Persist oversized dynamic responses so MCP clients can fetch paginated slices later.
- Contains: JSON cache files written by `save_response_to_file(...)` in `meraki-mcp-dynamic.py`
- Key files: Runtime-generated only; path configured by `RESPONSE_CACHE_DIR` in `meraki-mcp-dynamic.py`

**Planning Directory (`.planning/codebase/`):**
- Purpose: Store generated mapping documents consumed by GSD planning/execution workflows.
- Contains: `ARCHITECTURE.md`, `STRUCTURE.md`, and related planning artifacts
- Key files: `.planning/codebase/ARCHITECTURE.md`, `.planning/codebase/STRUCTURE.md`

**Claude Metadata Directory (`.claude/`):**
- Purpose: Keep local Claude-oriented workspace metadata separate from application runtime.
- Contains: Local support files, not application code
- Key files: Not part of the Meraki MCP runtime path

**Python Cache Directory (`__pycache__/`):**
- Purpose: Hold interpreter-generated bytecode.
- Contains: `.pyc` artifacts from local execution
- Key files: Generated only; do not place source here

## Key File Locations

**Entry Points:**
- `meraki-mcp.py`: Manual/curated MCP server entrypoint
- `meraki-mcp-dynamic.py`: Dynamic/full-coverage MCP server entrypoint
- `entrypoint.sh`: Container entrypoint that chooses which Python server script runs
- `inspect_tools.py`: Standalone inspection utility for the dynamic server surface

**Configuration:**
- `pyproject.toml`: Python version requirement and primary dependencies
- `requirements.txt`: Locked dependency versions used by install and container build
- `.env-example`: Environment variable template for local and container setup
- `docker-compose.yml`: Runtime environment wiring for containerized HTTP mode
- `Dockerfile`: Build-time defaults, exposed port, and default `MCP_SERVER=dynamic`

**Core Logic:**
- `meraki-mcp.py`: Pydantic schemas plus curated Meraki tool implementations
- `meraki-mcp-dynamic.py`: Reflective Meraki dispatcher, method discovery, and caching subsystem

**Testing:**
- `inspect_tools.py`: Inspection-only utility that helps verify SDK coverage without making Meraki API calls
- `README.md`, `README-DYNAMIC.md`: Manual verification and runtime setup guidance
- `tests/`: Not present. Add a top-level `tests/` directory if automated tests are introduced.

## Naming Conventions

**Files:**
- Use top-level executable script names for runtime modules: `meraki-mcp.py`, `meraki-mcp-dynamic.py`, `inspect_tools.py`
- Use descriptive Markdown filenames for operator docs: `README.md`, `README-DYNAMIC.md`, `COMPARISON.md`, `INSTALL.md`
- Use standard infrastructure filenames for container/runtime assets: `Dockerfile`, `docker-compose.yml`, `entrypoint.sh`

**Directories:**
- Keep runtime state in hidden top-level directories: `.meraki_cache/`, `.planning/`, `.claude/`
- Keep generated interpreter artifacts in `__pycache__/`
- Do not expect a `src/` package layout in the current structure; all application code lives at project root

## Where to Add New Code

**New Curated Meraki Tool:**
- Primary code: `meraki-mcp.py`
- Place new Pydantic models near the existing schema block at the top of `meraki-mcp.py`
- Place new `@mcp.tool()` functions in the matching section block already used in `meraki-mcp.py` such as organizations, networks, devices, wireless, switch, appliance, or camera

**New Dynamic Runtime Behavior:**
- Implementation: `meraki-mcp-dynamic.py`
- Use this file for generic dispatch changes, discovery helpers, read-only policy, cache behavior, pagination control, and new convenience wrappers around the generic caller

**New Deployment Or Runtime Mode Support:**
- Bootstrap selection: `entrypoint.sh`
- Image/runtime defaults: `Dockerfile`
- Local container wiring: `docker-compose.yml`

**New Inspection Or Maintenance Utility:**
- Implementation: Add a new top-level utility script beside `inspect_tools.py`
- Keep it separate from `meraki-mcp.py` and `meraki-mcp-dynamic.py` unless the behavior must be part of the MCP runtime

**Automated Tests:**
- Implementation: Create a top-level `tests/` directory
- Mirror the flat layout by splitting tests by runtime script, for example `tests/test_meraki_mcp.py` and `tests/test_meraki_mcp_dynamic.py`

**Shared Utilities:**
- Current location: Not extracted
- Guidance: Reuse local helpers inside the owning script unless you are intentionally introducing a shared Python module. The current structure duplicates bootstrap code between `meraki-mcp.py` and `meraki-mcp-dynamic.py`, so adding a new shared module is a structural change, not a routine edit.
